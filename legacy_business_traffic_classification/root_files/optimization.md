# `train_final_optimized.py` 优化方案

更新时间：2026-03-18
适用对象：`src/teammate_optimized/train_final_optimized.py`
说明：本文件只描述后续优化方案，不直接修改原有代码。

## 1. 目标
当前优化版脚本已经体现出较明确的思路：

- 面向 `CHAT`、`STREAMING` 等弱类增强
- 使用特征工程
- 使用多模型融合
- 输出最终分类报告

后续优化目标不是推翻原有思路，而是在保留总体路线的前提下，让脚本在以下方面更强：

1. 特征工程更系统
2. 集成策略更完整
3. 误分类分析更可落地
4. 输出结果更适合写课程报告
5. 代码结构更稳定、可维护

## 2. 当前脚本存在的主要问题

### 2.1 中文乱码和可读性问题
当前脚本里存在明显的中文乱码，这会带来两个问题：

- 阅读成本高
- 容易引发字符串、注释、终端输出相关的问题

### 2.2 特征工程仍然偏经验化
当前脚本虽然已经加入了一些有效特征，例如：

- `min_active_is_missing`
- `fiat_range`
- `fiat_ratio`
- `bytes_per_packet`
- `pkt_ratio`
- `pkt_ratio_sq`

但整体仍属于“局部增强”，还没有形成系统性的特征构造和筛选机制。

### 2.3 集成策略还不够充分
当前脚本的集成方法是：

- 两个 `XGBoost`
- 一个 `RandomForest`
- 手工尝试若干组概率加权权重

这种方法已经有效，但仍有几个局限：

- 权重组合数量少
- 异构模型差异性不够大
- 输出结果还不够细，难以支撑后续分析

### 2.4 缺少误分类样本导出
当前脚本虽然输出了总体报告和各类召回率，但还不能直接回答这些关键问题：

- `CHAT` 主要被错分成了谁
- `FT` 主要被错分成了谁
- 哪些样本是低置信度错误
- 哪些类别的边界最模糊

这会导致后续优化容易停留在“继续调参”的层面，而不是基于错误样本继续改进。

## 3. 建议保留的原有思路
后续优化不建议推翻下面这些已有思路：

### 3.1 保留“弱类增强”的方向
从当前结果看，真正需要继续补强的类别依然是：

- `CHAT`
- `FT`
- `STREAMING`

因此后续优化仍应围绕这几个类别展开，而不是只追求总体 Accuracy。

### 3.2 保留“多模型融合”的方向
当前脚本通过多模型融合已经取得比基线更好的结果，因此不建议退回到单模型思路。

### 3.3 保留“业务含义明确的特征工程”
当前脚本里最有价值的一点，是新加特征并不是瞎加，而是试图把业务行为差异显式化。这个方向应当继续保留。

## 4. 建议新增的优化内容

## 4.1 优化一：系统化扩展特征工程
后续建议在原有特征工程基础上，增加以下几类特征。

### 4.1.1 比值类特征
作用：增强方向性和交互性的表达。

建议新增：

- 前向包间隔 / 后向包间隔
- 前向平均间隔 / 后向平均间隔
- 最小值 / 最大值比
- 活跃段 / 空闲段比
- 字节速率 / 包速率比

### 4.1.2 波动类特征
作用：区分稳定传输和突发传输。

建议新增：

- `max - min`
- `std / mean`
- 波动强度相关特征

适合重点区分：

- `CHAT`
- `FT`
- `STREAMING`

### 4.1.3 非线性变换特征
作用：处理长尾分布和极端值影响。

建议新增：

- `log_duration`
- `log_flowBytesPerSecond`
- `log_flowPktsPerSecond`
- 关键比例特征的平方项

### 4.1.4 缺失模式特征
作用：把 `-1`、空值、异常值本身当作一种模式，而不是简单忽略。

建议新增：

- `xxx_is_missing`
- `xxx_nan_flag`

这一类特征尤其适合当前这种很多字段可能出现 `-1` 的数据集。

## 4.2 优化二：加入特征筛选机制
特征工程不应该只是不断往上加字段，还要做筛选。

建议加入：

- 常量列删除
- 近似重复列删除
- 高相关特征删除
- 特征重要性统计输出

这样做的价值有两点：

- 提高模型稳定性
- 让课程报告中的“特征分析”部分更完整

## 4.3 优化三：增强模型异构性
当前模型集合是：

- `XGBoost`
- `XGBoost`
- `RandomForest`

这里存在的问题是：

- 两个主模型同属提升树体系
- 模型之间的差异性不够大

建议新增至少一个更偏随机分裂风格的树模型，例如：

- `ExtraTreesClassifier`

这样做的目的不是增加模型数量本身，而是增强概率融合时的互补性。

## 4.4 优化四：扩大集成权重搜索范围
当前脚本只尝试少量手工设定权重，这不够充分。

建议后续改为：

- 以 `0.1` 为步长搜索所有权重组合
- 所有模型权重之和等于 `1`
- 以 `Macro-F1` 为主指标
- 以 `Accuracy` 作为辅助比较指标

这样做的好处是：

- 更符合你当前“继续补弱类”的目标
- 不容易只对大类有利

## 4.5 优化五：补齐误分类分析输出
后续建议在训练完成后，增加以下输出文件：

- `test_predictions_detailed.csv`
- `misclassified_samples.csv`
- `misclassification_pairs.csv`
- `confusion_matrix.csv`

建议导出的字段至少包括：

- 真实标签 `y_true`
- 预测标签 `y_pred`
- 置信度 `confidence`
- 是否预测正确 `is_correct`
- 低置信度边界信息，例如前两类概率差值

这一步的价值很高，因为它直接服务于下一轮优化。

## 4.6 优化六：补齐结果产物
当前脚本输出主要集中在最终报告，后续建议统一输出成完整实验目录，包含：

- `classification_report.txt`
- `classification_report.csv`
- `metrics.json`
- `confusion_matrix.csv`
- `feature_importance_summary.csv`
- `final_optimized_model.joblib`

这样更适合：

- 后续复现实验
- 写课程报告
- 答辩时展示结果

## 5. 推荐的改造顺序
如果后面要真正落地改造，不建议一次性乱改，推荐按这个顺序：

1. 先解决编码和输出可读性问题
2. 再重构数据加载与特征工程函数
3. 再加入特征筛选机制
4. 再扩展模型集合和集成策略
5. 最后补误分类分析和结果文件导出

这样做的原因是：

- 每一步都比较独立
- 出问题时更容易定位
- 更适合边改边验证

## 6. 预期改造结果
如果按这份方案继续推进，后续优化版脚本至少应该做到：

- 代码不再存在乱码问题
- 特征工程比当前更系统
- 集成策略比当前更充分
- 能导出误分类样本供下一轮分析
- 能直接产出适合写报告的结果文件

## 7. 一句话总结
后续优化不应该停留在“继续调几个参数”，而应该围绕特征工程、异构集成、误分类分析和结果产物标准化这四条主线继续推进。
