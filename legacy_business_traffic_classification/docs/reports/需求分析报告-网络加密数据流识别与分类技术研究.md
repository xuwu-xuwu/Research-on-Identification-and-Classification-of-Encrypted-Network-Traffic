# 1 项目介绍

## 1.1 项目定义

本项目拟开发一套面向加密网络流量的离线识别与分类软件原型。系统在不解密业务载荷内容的前提下，利用流级统计特征对网络通信行为进行自动分类，输出分类标签、性能指标和分析报告。当前课程项目阶段的主要任务是完成 7 类加密流量识别，包括 `BROWSING`、`CHAT`、`FT`、`MAIL`、`P2P`、`STREAMING` 和 `VOIP`。

从用途上看，本项目服务于以下目标：

1. 为课程实验提供一条完整、可复现的“数据读取-预处理-模型训练-性能评估-结果导出”技术链路。
2. 验证传统机器学习方法在加密流量分类任务上的可行性，并为后续优化方案提供基线参照。
3. 为网络安全场景中的流量治理、行为识别和异常分析提供可解释的实验性方法支撑。

本项目当前定位为单机离线分析系统，而不是在线生产系统。其核心交付物包括训练脚本、预测脚本、实验结果文件、模型文件和课程报告材料。

## 1.2 项目开发背景

随着 HTTPS、TLS 1.3、QUIC 等协议的大规模部署，直接基于报文载荷内容的检测方式在大量场景中已经不再适用。另一方面，网络安全防护、流量治理和业务识别仍然需要对通信行为进行分类判断，因此，如何在不解密业务内容的条件下，仅基于流量统计模式完成分类，成为当前加密流量分析研究中的典型问题。

本项目的任务提出者为《信息系统安全与对抗技术》课程，开发者为课程项目组成员，直接用户包括课程指导教师、项目组成员以及具备一定 Python 与网络基础的实验人员。项目开发的直接原因如下：

1. 课程要求完成一个与信息安全、流量分析和工程实现相关的综合项目。
2. 加密流量分类兼具研究价值与工程可实现性，适合在课程周期内形成可交付成果。
3. 仓库中已经具备公开数据集、基线代码和优化结果，具备继续完善为规范化课程项目的基础。

本项目与外部数据和工具的关系主要体现在以下方面：

| 外部对象 | 关系说明 |
| --- | --- |
| 公开数据集 | 为本系统提供带标签的流级特征数据和原始 `PCAP` 数据来源 |
| Wireshark / tcpdump | 在扩展方案中用于抓包，不属于当前最小可交付版本的必需组成 |
| CICFlowMeter 或同类工具 | 在需要从 `PCAP` 生成流级特征时作为前置处理工具 |
| Python 机器学习库 | 支撑特征处理、模型训练、评估与结果导出 |
| 课程报告与答辩材料 | 本系统输出的实验数据和分析图表将直接服务于课程考核 |

# 2 任务概述

## 2.1 目标

本项目的总体目标是构建一套能够对加密网络流量进行自动识别与分类的实验型系统，要求其在课程可接受的时间和资源条件下，完成数据处理、模型训练、性能评估、结果导出和无标签数据预测等任务。

具体目标如下：

1. 支持读取带标签的 `ARFF` 或 `CSV` 数据集，完成标签识别、数值转换、缺失值处理和训练集/测试集划分。
2. 建立一个可稳定复现的基线模型。当前仓库中的基线方案为 `SimpleImputer + RandomForestClassifier`。
3. 输出 `Accuracy`、`Precision`、`Recall`、`F1-Score`、`Macro-F1`、`Weighted-F1`、混淆矩阵等结果，用于课程报告和模型比较。
4. 支持对无标签数据进行预测，并输出预测类别及可选的置信度信息。
5. 为后续优化提供接口，包括特征工程、类别不平衡处理、多模型融合和误分类样本分析。

结合当前项目进展，系统的可行性已经得到初步验证。基于 `TimeBasedFeatures-Dataset-15s-AllinOne.arff` 的现有实验结果表明：

1. 基线模型在 7 分类任务上达到 `Accuracy = 0.8905`、`Macro-F1 = 0.8625`。
2. 优化方案结果达到 `Accuracy = 0.9211`、`Macro-F1 = 0.9010`。

因此，本需求报告中提出的性能要求不是空泛目标，而是结合现有结果后形成的可实现要求。

## 2.2 用户的特点

本系统的最终用户以课程项目成员和指导教师为主，属于小规模、低并发、技术型用户，主要特点如下：

1. 操作人员通常具备基本的 Python 使用能力，能够在命令行环境中运行脚本、传入参数并查看输出文件。
2. 操作人员需要具备基础网络知识，理解流量、会话、五元组、特征字段、分类标签等基本概念。
3. 使用频度以课程研发阶段的集中实验为主，预计每周进行 2 至 5 次完整训练或评估，不属于高频在线业务系统。
4. 维护人员由项目组成员承担，因此系统应当具备较好的可读性、可复现性和目录结构规范性，便于后续接手。
5. 指导教师更关注结果可信度、实验规范性和文档完整性，因此系统不仅要输出指标，还要输出可用于分析和汇报的结构化结果文件。

## 2.3 假定和约束

本项目开发和使用过程中的主要假定与约束如下：

1. 项目周期受课程教学安排限制，整体按 15 周课程节奏推进。
2. 当前最小可交付版本以离线实验系统为主，不要求实现在线部署、网页前端和实时流量识别服务。
3. 当前稳定支持的数据输入为 `ARFF` 和 `CSV` 流级特征文件，`PCAP -> 特征提取` 属于后续扩展链路。
4. 数据来源必须为公开数据集或经过授权采集的数据，项目不允许实施任何非法抓包、绕过认证、破解或解密行为。
5. 当前研究边界限定为“加密流量分类”，不涉及敏感业务内容恢复和报文载荷还原。
6. 课程项目以单机运行方式为主，不要求多用户网络并发访问；但训练脚本应支持有限度的本地并行计算。
7. 当前代码环境已围绕 Python 生态建立，后续新增功能应尽量兼容现有目录结构和输出规范。

# 3 需求规定

## 3.1 对功能的规定

本系统的功能需求按照“输入-处理-输出”方式描述如下。

| 需求编号 | 功能名称 | 输入 | 处理 | 输出 |
| --- | --- | --- | --- | --- |
| FR-01 | 数据导入与校验 | `ARFF`/`CSV` 数据文件、标签列名或自动识别规则 | 读取数据、识别字段、校验文件存在性和数据完整性 | 可训练或可预测的数据表、异常提示 |
| FR-02 | 数据预处理 | 原始特征列和标签列 | 数值化转换、去除非法样本、处理 `NaN/Inf`、删除全空列、缺失值填补 | 清洗后的特征矩阵和标签向量 |
| FR-03 | 基线模型训练 | 清洗后的训练数据、随机种子、测试集比例、模型参数 | 划分训练集和测试集，训练随机森林基线模型 | 已训练模型、测试集预测结果 |
| FR-04 | 优化模型扩展 | 清洗后的训练数据、扩展特征、类别权重、多模型参数 | 执行特征工程、训练优化模型、融合输出概率 | 优化模型结果与对比结论 |
| FR-05 | 性能评估 | 真实标签与预测标签 | 计算准确率、召回率、F1 值、宏平均指标并绘制混淆矩阵 | `metrics.json`、分类报告、混淆矩阵图或表 |
| FR-06 | 无标签数据预测 | 训练好的模型文件和无标签 `ARFF/CSV` 文件 | 按训练时的特征顺序完成推断，必要时输出概率 | 带 `predicted_label` 的结果文件，必要时含 `predicted_confidence` |
| FR-07 | 结果持久化 | 训练或预测阶段产生的中间结果 | 按统一目录结构保存模型、图表、文本报告和结构化指标 | `joblib`、`txt`、`csv`、`json`、`png` 等文件 |
| FR-08 | 实验复现与参数配置 | 命令行参数 | 固定随机种子、记录输入路径、标签列、输出目录等关键参数 | 可复现实验配置和标准化输出 |

对系统运行方式补充规定如下：

1. 本系统当前面向 1 名研究人员在本机上运行，不要求提供网页接口和多终端联机访问能力。
2. 训练脚本应支持命令行参数化配置，例如数据路径、标签列名、测试集比例、随机种子、树数量和输出目录。
3. 结果输出必须具备统一命名和目录约定，以便课程报告直接引用。

## 3.2 对性能的规定

### 精度

本项目的精度要求既包括数据处理正确性，也包括分类性能指标要求。

1. 数据读取后，系统应正确识别标签列和特征列，不能因格式解析错误导致样本或字段无声丢失。
2. 数值化转换后，系统应明确处理非数值、缺失值和无穷值，不能直接将异常字段带入模型训练。
3. 在当前 7 分类任务上，基线模型验收要求建议设定为：
   1. `Accuracy >= 0.88`
   2. `Macro-F1 >= 0.85`
   3. `Weighted-F1 >= 0.88`
4. 对优化模型的阶段性目标建议设定为：
   1. `Accuracy >= 0.90`
   2. `Macro-F1 >= 0.89`
5. 系统输出的性能指标至少保留 4 位小数，便于报告撰写和横向比较。

以上阈值与当前项目结果相匹配：现有基线结果为 `Accuracy 0.8905 / Macro-F1 0.8625`，优化结果为 `Accuracy 0.9211 / Macro-F1 0.9010`，说明需求具有现实可达性。

### 时间特性要求

考虑到课程项目的实验规模和常规个人计算机条件，系统时间特性要求如下：

1. 对规模约 `2 万` 条样本、`20 至 30` 个特征的数据集，数据读取与预处理应在 `2 分钟` 内完成。
2. 基线模型单次训练与评估应在 `10 分钟` 内完成。
3. 优化模型在加入额外特征工程、模型融合和结果导出后，单次完整运行应控制在 `30 分钟` 内。
4. 使用已训练模型对测试集规模的无标签样本进行预测时，应在 `1 分钟` 内完成推断并导出结果。
5. 混淆矩阵、指标文件和分类报告的导出应在训练结束后 `2 分钟` 内完成。

### 灵活性

系统应满足以下灵活性要求：

1. 支持自动识别标签列，也允许通过命令行显式指定标签列。
2. 支持 `ARFF` 和 `CSV` 两类常用输入格式，后续可扩展到由 `PCAP` 派生出的特征文件。
3. 支持修改训练测试划分比例、随机种子、模型参数和输出目录，而无需重写主流程代码。
4. 支持在不破坏现有输出规范的前提下，增加新特征、新类别和新模型。
5. 当运行环境、软件版本或实验计划发生变化时，系统应尽可能通过配置或小范围代码调整完成适配。

## 3.3 输入输出要求

### 输入要求

| 输入项 | 类型与媒体 | 格式要求 | 说明 |
| --- | --- | --- | --- |
| 训练数据文件 | 本地磁盘文件 | `ARFF` 或 `CSV` | 当前主要输入，要求含特征列和标签列 |
| 标签列名 | 命令行参数 | 字符串 | 可省略，由系统自动推断，如 `class1` |
| 模型参数 | 命令行参数 | 数值或字符串 | 如测试集比例、随机种子、树数量、输出目录 |
| 预测数据文件 | 本地磁盘文件 | `ARFF` 或 `CSV` | 可不含标签列，但字段顺序需与训练所需特征兼容 |
| 扩展原始流量文件 | 本地磁盘文件 | `PCAP/PCAPNG` | 属于扩展功能输入，不是当前最小版本必需项 |

当前项目已验证的数据集文件为 `data/Scenario B-ARFF/Scenario B-ARFF/TimeBasedFeatures-Dataset-15s-AllinOne.arff`，总样本数为 `18758`，特征字段共 `23` 个，标签字段为 `class1`。已识别的主要特征包括 `duration`、`total_fiat`、`total_biat`、`flowPktsPerSecond`、`flowBytesPerSecond`、`min_flowiat`、`max_flowiat`、`mean_active`、`mean_idle` 等。

### 输出要求

| 输出项 | 类型 | 说明 |
| --- | --- | --- |
| `metrics.json` | `JSON` 文件 | 保存样本规模、特征数、类别数、准确率、宏平均 F1 等关键指标 |
| `classification_report.txt` | 文本文件 | 保存分类报告，便于直接粘贴到课程文档 |
| `classification_report.csv` | `CSV` 文件 | 适用于后续统计和图表处理 |
| `confusion_matrix.png` / `confusion_matrix.csv` | 图像或表格文件 | 用于展示各类别误判关系 |
| `model.joblib` / `final_optimized_model.joblib` | 模型文件 | 保存训练完成的模型及必要元数据 |
| 预测结果文件 | `CSV` 或同类文本文件 | 至少包含 `predicted_label`，可选包含 `predicted_confidence` |
| 分析输出文件 | `CSV/TXT` | 如特征重要性、误分类样本、误判对统计等 |

输出数据中的分类指标建议保留 4 位小数，图表标题、坐标轴和类别名称应可直接用于课程报告展示。

## 3.4 数据管理能力要求

本项目既包含流级特征数据，也包含原始压缩数据与实验产物，因此对数据管理能力有如下要求：

1. 系统应按“原始数据、处理中间数据、模型输出、报告材料”分层管理文件，避免不同阶段产物混放。
2. 当前仓库中的压缩数据规模约为 `12.3 GB`，系统应预留不少于 `30 GB` 的可用磁盘空间，用于存放压缩包、解压后的数据、输出结果和文档。
3. 当前项目输出目录已包含模型文件、指标文件、分类报告、误分类样本和图表，系统应支持继续扩展这些结果文件而不破坏原有命名约定。
4. 对于训练结果，至少应保存模型文件、输入数据来源、标签列名、特征字段列表和关键指标，保证后续复现实验时能够追溯。
5. 对于自采数据或经过加工的数据，必须保留数据来源说明、处理过程说明和备份副本，避免后续无法复现。
6. 数据备份应至少覆盖以下内容：原始数据清单、当前最优模型、最终实验报告、关键图表和参数说明。

## 3.5 故障处理要求

系统应对可能出现的软件、数据和硬件故障给出明确处理方式，至少满足以下要求：

1. 当输入文件不存在、路径错误或格式不受支持时，系统应立即报错并提示正确的输入类型。
2. 当标签列缺失、类别数不足、特征列全部为空或样本为空时，系统应终止训练并说明原因，禁止输出误导性的“成功结果”。
3. 当运行环境缺少关键依赖库时，系统应提示缺失的库名称或版本问题，便于维护人员修复。
4. 当预测阶段找不到模型文件或输入字段与训练特征不匹配时，系统应拒绝执行推断并记录异常。
5. 当训练中断或输出目录不可写时，系统应尽量保留已经生成的中间结果，并给出清晰的错误定位信息。
6. 对于硬件资源不足导致的运行失败，例如内存不足或磁盘空间不足，应在文档中提前给出最低配置建议。

## 3.6 保密要求

尽管本项目主要使用公开数据集和课程实验数据，但仍需满足下列安全与保密要求：

1. 项目不得通过破解、绕过认证、解密通信载荷等方式获取敏感业务内容。
2. 仅允许使用公开数据集或经过授权采集的数据，不得采集未经许可的真实用户流量。
3. 如果后续引入自采样本，应对 `IP`、账号标识、设备标识和时间信息进行脱敏或匿名化处理。
4. 报告中展示的数据、图表和样本案例不得暴露个人隐私或未授权的真实业务信息。
5. 项目成员如使用来自第三方的数据和工具，应在文档中明确数据来源和使用边界。

## 3.7 其他专门要求

除上述需求外，系统还应满足以下专门要求：

1. 易用性要求：核心流程应可通过 1 条命令完成，输入参数命名清晰，输出目录结构明确。
2. 可维护性要求：训练、预测、评估等逻辑应尽量分模块组织，关键步骤有必要的说明文档。
3. 可读性要求：报告用语规范，代码和文档命名统一，便于课程验收和组内协作。
4. 可靠性要求：关键实验应固定随机种子，结果可复现，不能依赖人工记忆复原参数。
5. 可扩展性要求：后续应能够增加特征工程、类别重加权、异构集成和误分类分析，而不需要完全推翻现有架构。
6. 可移植性要求：当前以 Windows 环境为主，但整体方案应尽量保持对 Linux 环境的可迁移性。

# 4 运行环境规定

## 4.1 设备

结合当前项目的模型规模、数据规模和课程实验场景，建议运行环境满足如下硬件要求：

1. 处理器：`x86_64` 架构 CPU，建议 `4` 核及以上。
2. 内存：最低 `8 GB`，推荐 `16 GB` 及以上。
3. 外存：建议至少保留 `30 GB` 可用空间，用于保存原始压缩数据、解压数据、输出模型和报告。
4. 输入输出设备：普通键盘、鼠标和显示器即可满足开发、训练和结果查看需求。
5. 网络要求：离线训练和预测阶段不依赖持续联网，但在下载公开数据集和文献时需要互联网连接。
6. GPU 要求：当前基线方案与已完成优化方案均可在 CPU 环境下运行，不强制要求 GPU。

## 4.3 接口

本系统当前主要提供文件接口和命令行接口，具体要求如下：

1. 文件输入接口：支持从本地磁盘读取 `ARFF` 和 `CSV` 文件。
2. 模型接口：使用 `joblib` 保存和加载模型，要求同时保存特征字段顺序和标签信息。
3. 结果接口：支持输出 `TXT`、`CSV`、`JSON`、`PNG` 等常用格式，便于后续分析和汇报。
4. 扩展数据接口：在扩展阶段可与 `PCAP` 文件、抓包工具和流特征提取工具对接。
5. 人机接口：当前采用命令行执行方式，不要求图形界面，但输出信息应足够明确，便于用户定位问题。

## 4.4 控制

本系统通过命令行参数控制运行流程。控制信号主要来自用户输入的脚本命令、数据路径和模型参数。当前已形成的典型控制方式如下：

```powershell
python src/baseline/train_baseline.py `
  --data "data/Scenario B-ARFF/Scenario B-ARFF/TimeBasedFeatures-Dataset-15s-AllinOne.arff" `
  --label class1 `
  --test-size 0.2 `
  --random-state 42 `
  --n-estimators 300 `
  --output-dir "outputs/baseline/baseline_run"
```

对控制方式进一步规定如下：

1. 运行命令应支持显式指定输入数据、标签列、输出目录和关键超参数。
2. 对于预测功能，应支持加载指定模型文件并输出预测结果文件。
3. 控制参数的默认值应在脚本帮助信息中给出，避免使用者必须阅读源码才能运行。
4. 系统运行日志应至少能够反映当前处理的数据路径、输出路径、主要模型参数和最终结果位置。
