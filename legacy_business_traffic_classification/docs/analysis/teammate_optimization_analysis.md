# 同事优化版方法分析

## 1. 分析对象
- 基线代码：`src/baseline/train_baseline.py`
- 同事优化版代码：`src/teammate_optimized/train_final_optimized.py`
- 同事提交说明：`docs/reports/数据集调整报告.docx`
- 同事最终结果：`outputs/optimized/final_report.txt`

## 2. 结论概述
- 同事的优化路线总体有效，核心思路不是简单“换模型”，而是围绕难分类类别做定向优化。
- 基线版本整体准确率约为 `89.45%`，优化版报告结果为 `92.11%`。
- 主要收益来自四部分：特征工程、类别加权、模型升级、概率集成。
- 这套方法对 `CHAT` 和 `STREAMING` 两个原始短板类别有明显改善。

## 3. 她的改进策略

### 3.1 从单模型切换到多模型
- 基线方案使用单一 `RandomForest`。
- 优化版同时训练了三个模型：
- `XGBoost` 加权版：重点照顾 `CHAT` 和 `STREAMING`
- `XGBoost` 普通版：作为稳定基准模型
- `RandomForest`：保留树模型对非线性关系和异常模式的捕捉能力
- 这样做的逻辑是让不同模型学习同一批数据的不同侧面，再做融合。

### 3.2 针对难分类类别做加权
- 在训练集上，对 `CHAT` 样本赋予更高权重 `2.0`，对 `STREAMING` 赋予权重 `1.5`。
- 这属于“有针对性的类别关注”，目的不是盲目抬高总体准确率，而是提升原先召回率不足的类别。
- 这种方法适合当前数据分布，因为 `CHAT`、`STREAMING` 本身样本量较小且边界较模糊。

### 3.3 增加面向业务行为的特征工程
- 她没有停留在原始统计特征上，而是新造了一批更有解释性的特征：
- `min_active_is_missing`：把 `min_active == -1` 单独编码为“是否缺失”
- `fiat_range`、`fiat_ratio`：强化前向包间隔的波动信息
- `bytes_per_packet`：反映流量强度与单包负载关系
- `pkt_ratio`、`pkt_ratio_sq`：试图描述前后向交互比例
- 这些特征本质上是在把“行为差异”显式化，尤其适合区分聊天、流媒体和文件传输。

### 3.4 处理异常值和极端值
- 她把 `min_active == -1` 当作一种特殊信号，而不是简单忽略。
- 同时对数值列做了 `0.999` 分位数截断，减少极端值对模型训练的影响。
- 这说明她已经开始从“直接跑模型”转向“先理解数据，再训练模型”。

### 3.5 使用概率级集成
- 她没有做简单投票，而是对三个模型的 `predict_proba` 结果做加权平均。
- 再通过若干组手工权重组合选择最优结果。
- 这种做法比单模型更稳，尤其在类别边界重叠时更容易取得提升。

## 4. 为什么这些方法有效
- `CHAT` 通常是小包、高交互、时序离散，原始特征不一定足够分开；新造的间隔类、比例类特征会更敏感。
- `STREAMING` 通常表现为持续传输、字节率较高，`bytes_per_packet` 这类特征有助于强化这一行为模式。
- `XGBoost` 对复杂非线性关系和特征组合的建模能力通常强于单一随机森林。
- 异构集成让不同模型互补，减少某一个模型“偏科”带来的误判。

## 5. 实际效果
- 同事最终报告显示准确率达到 `92.11%`。
- 分类结果中：
- `CHAT` 的召回率提升到 `0.8058`
- `STREAMING` 的召回率提升到 `0.8325`
- `VOIP` 仍然保持极高识别率
- 这说明她的优化不是只提升大类，而是补了基线最明显的短板。

## 6. 方法上的优点
- 先定位问题类别，再设计改进方向，思路比盲目调参更合理。
- 特征工程有业务解释性，适合写进课程报告。
- 使用多模型融合，体现了较强的实验设计意识。
- 最终结果提升真实可见，不是轻微波动。

## 7. 需要注意的问题

### 7.1 代码与报告并不完全一致
- 报告中提到“删除 ID 特征、避免数据泄露”，但当前优化脚本里没有看到显式删除 ID 类字段的代码。
- 因此这部分更像分析结论，而不是完整落地实现。

### 7.2 存在标准化时机不当的问题
- 她在全量数据上先 `fit_transform(StandardScaler)`，再做训练测试划分。
- 这样会让测试集信息提前进入标准化过程，属于轻度数据泄露。
- 虽然对树模型影响通常有限，但从实验规范上看不够严谨。

### 7.3 权重搜索仍偏经验化
- 当前只尝试了几组手工设定权重。
- 这能得到提升，但不属于系统搜索，后续还可以用网格搜索或交叉验证进一步验证。

### 7.4 有未落地的尝试痕迹
- 代码里定义了 `focal loss` 训练函数，但没有被最终调用。
- 说明有些策略是“尝试过但没进入最终方案”，写报告时要和最终实现区分开。

## 8. 对项目的启发
- 第一阶段可以用基线模型快速跑通闭环。
- 第二阶段要重点关注“哪些类别识别不好”，而不是只盯总准确率。
- 第三阶段应从数据分析、特征工程、模型集成三个层面改进。
- 第四阶段在追求更高分数的同时，要注意避免数据泄露，保证结果可信。

## 9. 当前建议
- 保留同事的总体优化思路：`特征工程 + 类别加权 + 集成学习`
- 但建议再出一个“严格版最终脚本”：
- 标准化只在训练集上拟合
- 明确删除或验证可能泄露标签的字段
- 用统一的训练/验证流程复现实验结果
