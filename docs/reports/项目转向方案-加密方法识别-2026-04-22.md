# 项目转向方案：从业务类型分类转向加密方法识别

更新时间：`2026-04-22`  
适用项目：`网络加密数据流识别与分类技术研究`

> 2026-06-03 整理说明：本文是项目从业务类型分类转向加密方法识别时的历史方案文档。文中提到的旧业务分类代码路径已经归档到 `legacy_business_traffic_classification/`，当前有效实验入口以根目录 `readme.md`、`CURRENT_PROJECT_SUMMARY.md` 和 `src/encryption_method/` 为准。

## 1. 文档目的

本文档用于正式说明项目研究方向的调整方案。原项目的主任务是“加密流量业务类型识别”，即判断一条流量属于 `BROWSING`、`CHAT`、`FT`、`MAIL`、`P2P`、`STREAMING`、`VOIP` 等业务类别。根据导师的新要求，项目后续的正式研究目标将转向“识别流量所采用的加密方法”，重点关注不同加密协议、加密传输机制和加密通信工具在流量层面的可识别特征。

本次转向不是推翻已有工作，而是在保留现有代码框架、实验方法和模型体系的前提下，重新定义研究对象、标签体系和数据来源，使项目从“业务分类”平滑迁移到“加密方法识别”。

## 2. 原方向与新方向的关系

### 2.1 原项目的研究对象

原项目的任务可以概括为：

- 输入一条加密流量
- 基于流级统计特征或序列特征
- 判断其所属业务类型

即：

`流量 -> 业务类别`

典型标签包括：

- `BROWSING`
- `CHAT`
- `FT`
- `MAIL`
- `P2P`
- `STREAMING`
- `VOIP`

### 2.2 新项目的研究对象

转向后，任务改为：

- 输入一条流量
- 基于可观测的流量行为特征和可见协议特征
- 判断它所采用的加密方法、加密协议或加密传输机制

即：

`流量 -> 加密方法类别`

从研究表述上看，新的核心问题不再是“用户在做什么业务”，而是“这条流量采用了什么样的加密传输方式”。

### 2.3 为什么这个转向是合理的

这个转向有三个优点：

1. 与导师要求高度一致。  
   研究对象从业务语义切换到加密方法本身，更贴近“网络空间安全”方向。
2. 可以最大程度复用现有工作。  
   流级统计特征、树模型、集成模型、MLP、TextCNN、BiLSTM/Transformer、TrafficFormer 等代码都不需要推翻，只需要替换数据标签和研究问题。
3. 研究表达更清晰。  
   项目从“业务分类演示”升级为“加密方法识别研究”，在课程报告和答辩中更容易形成安全方向上的聚焦。

## 3. 新研究题目建议

以下题目都可以自然承接现有工作：

### 3.1 推荐题目

- `网络流量加密方法识别与分类技术研究`

### 3.2 更完整的工程型题目

- `面向加密协议与加密工具识别的网络流量分类技术研究`

### 3.3 更贴近当前方法体系的题目

- `基于流级统计特征与序列建模的网络流量加密方法识别研究`

其中最推荐使用第三个题目，因为它能直接解释你当前项目为什么同时包含：

- 流级统计特征路线
- 包级/序列建模路线
- 预训练模型迁移路线

## 4. 新任务的研究口径

“识别加密方法”本身有多种口径，难度差别较大。为了保证项目能稳定落地，建议采用由易到难的分层定义。

### 4.1 口径一：识别加密协议或加密传输机制

这是当前最容易落地、也最适合你现有项目框架的方向。

可选标签包括：

- `TLS`
- `QUIC`
- `SSH`
- `DTLS`
- `OpenVPN`
- `WireGuard`
- `Tor`
- `Non-encrypted`

这个方向的优点是：

1. 流级统计特征、包长序列、时间间隔序列都仍然有用。
2. 任务定义明确，易于采集数据和写报告。
3. 与现有模型体系兼容性最好。

### 4.2 口径二：识别 TLS/QUIC 内部加密套件

例如识别：

- `TLS 1.2`
- `TLS 1.3`
- `AES-GCM`
- `ChaCha20-Poly1305`
- `ECDHE-RSA`
- `ECDHE-ECDSA`

这个方向更偏协议与密码学细节，难度明显更高。问题主要在于：

1. 相关信息往往主要出现在握手阶段。
2. `TLS 1.3`、`ECH` 等机制会降低直接可见性。
3. 数据集和标注难度显著上升。

因此，这个方向更适合作为后续扩展，不适合作为当前课程项目主线。

### 4.3 口径三：识别加密实现或加密工具

例如识别：

- `OpenVPN`
- `WireGuard`
- `Shadowsocks`
- `Tor`
- `HTTPS`
- `QUIC`
- `SSH`

这个方向兼顾协议语义与工程可实现性，适合作为口径一的进一步细化版本。它比“识别底层密码算法”更现实，也更贴近安全应用场景。

### 4.4 当前建议采用的主任务口径

当前建议将正式主任务定义为：

- **识别流量所采用的可见加密协议或加密传输机制**

在目前本地数据条件下，更适合先从下面这组类别起步：

- `TLS`
- `QUIC`
- `SSH`
- `DTLS`

后续再根据数据采集情况补充：

- `OpenVPN`
- `WireGuard`
- `Tor`

## 5. 为什么不建议直接识别底层密码算法

虽然“识别流量使用的是 `AES` 还是 `ChaCha20`”听起来更贴近“加密方法”，但当前项目不建议直接以此为主线，原因如下：

1. 很多底层算法在流量侧并不稳定可见。
2. 实际可见性高度依赖握手字段，而不是流量统计行为本身。
3. 公开数据集较少，标注成本高。
4. 当前已有模型和数据框架更适合做“协议级/工具级识别”，而不是“密码套件级识别”。

因此，项目应当把“加密方法”解释为：

- 加密协议
- 加密传输机制
- 加密隧道工具

而不是直接解释为：

- 对称/非对称底层密码算法本身

## 7. 新的数据路线

转向后的关键不是换模型，而是换数据组织方式。

### 7.1 新数据的基本原则

新的数据集应尽量满足：

1. 标签针对的是加密方法，而不是业务类型。
2. 尽量减少模型只学到“业务内容差异”而没有学到“加密机制差异”的风险。
3. 数据划分尽量按抓包文件、会话或采集批次进行，而不是随机按包划分。
4. 避免把 IP、域名、协议解析器直接暴露出的标签字段作为训练特征。

### 7.2 当前已经完成的新数据处理

当前仓库中已经新增了专门面向新任务的数据目录：

- `data/encryption_method_identification/`

对应的数据处理脚本为：

- `tools/build_encryption_method_dataset.py`

这条新数据路线的当前版本采取的是：

- 从本地 `PCAP/PCAPNG` 中提取双向五元组流
- 使用 `tshark` 协议解析结果构造第一版“可见加密协议标签”
- 同时输出流级特征表和序列建模输入

当前已纳入的数据源包括：

- `data/NonVPN-PCAPs-01`
- `data/NonVPN-PCAPs-03`
- `data/VPN-PCAPs-02`

### 7.4 当前数据的解释边界

需要明确，这一版数据是：

- **第一版可见协议标签数据**

它适合用于：

- `TLS / QUIC / SSH / DTLS` 识别

但暂时不适合直接用于稳定地识别：

- `OpenVPN`
- `WireGuard`
- `Tor`

原因是：

1. 当前本地 `VPN-PCAPs-02` 文件名虽包含 `vpn_`，但抓包中很多时候暴露的是隧道内部承载流量，而不是稳定可见的 VPN 外层协议。
2. `WIREGUARD` 当前样本量过小，容易受解析误差影响。
3. 当前还没有受控采集的 `OpenVPN / WireGuard / Tor` 真实对照数据。

因此，当前最稳妥的做法是把第一版主任务暂定为：

- `TLS / QUIC / SSH / DTLS` 四类识别

而把 `OpenVPN / WireGuard / Tor` 作为第二阶段补采目标。

## 9. 新的实验设计建议

### 9.1 第一阶段实验

先围绕当前已可稳定支持的四类标签开展实验：

- `TLS`
- `QUIC`
- `SSH`
- `DTLS`

建议优先跑：

1. `RandomForest` 基线
2. `Optimized Ensemble`
3. `MLP`

目标是先建立一条新的稳定主线。

### 9.2 第二阶段实验

在第一阶段跑通后，再继续做：

1. `TextCNN + RIFA`
2. `BiLSTM/Transformer`
3. `TrafficFormer`

用于说明序列建模和预训练迁移是否对加密方法识别也有效。

### 9.3 建议保留的指标

继续使用下列指标：

- `Accuracy`
- `Precision`
- `Recall`
- `Macro-F1`
- `Weighted-F1`
- 各类别召回率
- 混淆矩阵

对于新任务来说，最重要的仍然是：

- `Macro-F1`

因为当前类别仍然不平衡，不能只看总体准确率。

## 10. 报告和答辩中的表述方式

在正式文档中，建议用下面的逻辑解释本次转向：

1. 原阶段工作重点是加密流量业务类型识别，用于验证流级统计特征建模、集成学习和序列建模的可行性。
2. 根据后续研究需要，项目进一步将研究目标从“业务分类”扩展到“加密方法识别”。
3. 新阶段保留原有技术路线，但将分类标签由应用类型调整为加密协议、加密传输机制或加密工具类型。
4. 因此，项目不是推翻重做，而是完成了从“业务语义识别”到“加密机制识别”的研究升级。

可以直接用于报告的简化表述如下：

> 原阶段研究主要关注加密流量的业务类型识别，例如网页浏览、聊天、文件传输和流媒体等。根据后续研究要求，本文进一步将研究目标从“加密流量业务分类”扩展为“加密方法识别”，重点关注不同加密协议、加密传输机制和加密通信工具在流量统计特征与序列特征上的差异。该转向不改变整体技术路线，仍采用流级统计特征、序列建模和预训练迁移方法进行分类建模，但分类标签由应用类型调整为加密方法类型。

## 11. 当前最推荐的推进顺序

建议按下面顺序推进：

1. 先把当前第一版新数据固定下来，以 `TLS / QUIC / SSH / DTLS` 作为第一阶段主任务。
2. 基于 `flow_features_labeled.csv` 先跑 `RandomForest` 与 `Optimized Ensemble`。
3. 用 `packet_sequences.tsv` 跑一版 `TextCNN + RIFA` 作为序列对照。
4. 整理第一轮结果，确认这条新主线是否可稳定收敛。
5. 再考虑第二轮补采数据，补齐 `OpenVPN / WireGuard / Tor` 三类更符合导师预期的“加密工具”标签。
6. 最后统一更新需求分析、开题报告和项目进度总结中的研究目标表述。

## 12. 当前最稳妥的结论

本项目的正确转向方式不是直接去识别 `AES`、`RSA`、`SM4` 等底层密码算法，而是将研究对象调整为：

- 加密协议
- 加密传输机制
- 加密通信工具

这一定义既符合导师提出的“识别流量的加密方法”的要求，又能最大程度复用现有代码、模型、实验框架和报告结构。

一句话概括当前转向方案就是：

> 将原来的“业务类型分类”任务，重构为“加密协议/加密传输机制分类”任务；保留原有模型体系，重建数据标签和研究问题，并逐步扩展到更强的加密工具识别任务。
