# 2 项目介绍

## 2.1 项目定义

本项目研制的是一个面向离线分析和本地演示场景的“网络流量加密方法识别与分类”软件系统。系统不尝试恢复明文内容，也不把网页浏览、聊天、文件传输等业务类型作为最终输出，而是根据网络流的统计特征、传输层上下文以及由抓包数据抽取的轻量序列特征，判断该流量属于 `NON_ENCRYPTED`、`TLS_FAMILY`、`SSH`、`QUIC`、`VPN`、`TOR`、`I2P`、`FREENET`、`ZERONET` 九类中的哪一类。

从研制结果看，项目已经形成一套完整的工程化产品：前端页面用于提交样本、查看模型信息和展示实时预测结果；后端服务负责模型加载、输入校验、特征变换、主模型和 fallback 模型自动路由；命令行工具支持批量预测；实时抓包模块通过 `tshark` 按五元组聚合网络流并调用模型推理；训练脚本和实验输出目录保留了模型构建、指标评估和结果复查所需的材料。

本项目的技术边界需要特别说明：系统识别的是可见协议族、隧道机制和匿名通信机制，不是直接识别底层密码套件或具体算法实现。例如，系统可以输出 `TLS_FAMILY`、`QUIC` 或 `TOR`，但不把 `AES-GCM`、`ChaCha20-Poly1305` 等密码算法作为最终类别。这一边界符合当前公开数据和课程项目周期内的工程可行性。

## 2.2 项目开发背景

本项目最初从加密流量业务类型分类切入，前期积累了流量特征提取、机器学习建模和论文方法复现经验。随着课程推进，项目研究目标根据导师要求调整为“识别流量采用何种加密方法或匿名通信机制”。这一调整使原有业务分类标签不再适合作为主任务，项目组必须重新梳理数据来源、标签空间、训练脚本和输出指标。

待开发软件系统的名称可概括为“加密方法识别与分类软件系统”。任务提出者为课程教学要求和项目研究目标调整需求，开发者为项目组两名学生成员，用户包括项目组成员、课程任课教师、验收评审人员以及后续复现实验人员。系统同其他外部系统没有强耦合关系，主要依赖本地文件系统中的数据集、模型产物和 `tshark` 工具；在演示层面，系统通过 HTTP API 和静态前端页面提供交互能力。

开发本项目的直接原因有三点。第一，传统业务分类不能准确回答“采用何种加密机制”的安全分析问题；第二，多源公开数据在标签、字段和格式上差异较大，需要统一数据构建程序支撑可复查实验；第三，课程验收不仅要求模型结果，还要求能够展示、调用和解释的完整软件系统。因此，项目最终同时完成了研究主线重构、模型训练优化和前后端软件封装。

# 3 实际开发结果

## 3.1 产品

项目最终制成的产品由训练研究产物和可运行软件系统两部分组成。训练研究产物包括统一数据集构建脚本、多个模型训练脚本、实验指标文件和模型文件；可运行软件系统包括 FastAPI 后端、静态前端、管理页面、实时抓包模块、命令行预测入口和便携部署脚本。按当前仓库统计，`src/encryption_method` 与 `software_system` 两个核心目录共包含 37 个主要文件，约 287.7 KB，源代码和说明文本约 6,988 行。

## 3.3 基本流程

本程序系统的实际处理流程如下表所示。整体流程分为离线训练流程和在线预测流程，两者共享特征定义、标签空间和模型元数据。

| 阶段 | 处理流程 |
| --- | --- |
| 1 数据输入 | 读取 `data/` 下结构化 CSV、流特征文件以及 Tor/NonTor 等 PCAP/PCAPNG 抓包文件。 |
| 2 数据构建 | 通过字段映射、`tshark` 抓包解析、双向流聚合和标签归并，生成统一的训练/验证/测试数据。 |
| 3 特征工程 | 形成 21 个流级数值特征、`transport` one-hot 特征和由 `sequence_text` 派生的 18 个序列统计特征。 |
| 4 模型训练 | 在全量 9 类主表上训练 `full_enhanced_fusion_xgboost`，并单独训练缺失输入场景的 `broad_fallback_xgboost`。 |
| 5 模型落盘 | 保存 `model.joblib`、`model.json`、`feature_metadata.json`、`metrics.json`、分类报告和混淆矩阵。 |
| 6 后端加载 | FastAPI 服务启动后加载主模型、fallback 模型和数据元数据，建立预测路由。 |
| 7 输入判定 | 若 21 个数值特征完整，则调用主模型；若任一数值字段缺失或不可转换，则调用 fallback 模型。 |
| 8 预测输出 | 通过前端页面、HTTP API、CSV 批量接口、CLI 或实时抓包模块返回类别、置信度和输入状态说明。 |

实时抓包流程在上述在线预测流程前增加了一个流聚合环节：后端调用 `tshark -l -i <interface> -T fields` 读取包字段，按协议和通信端点归一化为双向流；当流空闲超过设定阈值且包数达到最小要求后，系统计算流级特征并调用模型进行分类。该设计避免逐包分类带来的噪声，更符合当前模型以 flow 为分类粒度的训练方式。

## 3.4 进度

项目实际进度总体满足课程周期要求。与原定计划相比，最大变化是中途从业务类型分类调整为加密方法识别，这导致数据构建、标签设计和模型脚本需要重写，早期阶段出现方向重构开销；但后续通过集中整理数据、复用前期特征工程经验和采用 XGBoost 加强融合路线，最终完成了模型、软件系统和文档交付。

| 阶段 | 原定计划 | 实际完成情况 | 进度评价 |
| --- | --- | --- | --- |
| 需求与选题 | 明确加密流量分类任务和可用数据 | 从业务分类调整为加密方法识别，重新定义 9 类标签空间 | 略有调整，但方向更贴合课程要求。 |
| 数据准备 | 整理公开数据并形成训练表 | 完成多源 CSV、流特征和 Tor/NonTor 原始抓包的统一构建 | 达到，工作量高于原计划。 |
| 模型研发 | 完成可训练模型和指标输出 | 完成层级深度学习、全量加强融合、PCAP 子表对比和 fallback 模型 | 超出，形成多层对比结果。 |
| 软件封装 | 至少提供可运行脚本 | 完成 FastAPI 后端、前端页面、管理页、CLI、实时抓包和启动脚本 | 超出，形成完整演示系统。 |
| 测试与文档 | 完成报告和基本测试 | 完成中期报告、详细设计报告、项目研制报告、README 和便携部署说明 | 达到，文档体系较完整。 |

整体看，项目在研究方向重构阶段消耗了额外时间，但最终进度没有影响课程验收节点。主要原因是后续将任务分解为“数据统一、主模型、fallback、软件系统、文档”五条相对清晰的工作线，避免了继续在旧业务分类代码上进行低效修改。

从软件质量看，后端代码已经支持模型加载、输入校验、缺失字段路由、JSON/CSV 预测、实时抓包和管理接口；前端能够完成样本输入、结果展示和管理信息查看；部署脚本能够创建本地虚拟环境并自动发现 `tshark`。本次研制报告生成前，已对 `src/encryption_method` 和 `software_system/backend` 执行 Python 语法编译检查，结果通过，未发现语法级错误。

## 4.3 对技术方法的评价

本项目采用“统一数据构建 + 多粒度特征融合 + XGBoost 主模型 + fallback 路由 + Web/API 封装”的技术路线。实践表明，该路线适合课程项目的时间、数据和展示约束。统一数据构建解决了多源数据字段和标签不一致的问题；流级统计特征保证了全量样本可用；传输层和序列统计特征补充了协议行为差异；XGBoost 在当前特征规模下训练速度快、结果稳定、便于保存和部署。

与早期层级深度学习模型相比，当前加强融合 XGBoost 的优势在于训练和推理更轻量、对表格特征更友好、指标更稳定，并且便于在 FastAPI 后端中加载。与论文方法风格模型相比，当前主模型适用于全量 9 类主表，而 Deep Packet、ET-BERT、TFE-GNN 等方法更依赖原始包字节或包图输入，适合放在 PCAP 子表中进行同口径对比。因此，项目最终把全量 9 类主表和 5 类 PCAP 子表分层评价，避免了不同输入粒度方法直接混在同一主表中的不公平比较。

软件工程方法方面，FastAPI 后端、原生前端和 PowerShell 启动脚本的组合较为轻量，适合 Windows 本地课程演示。实时抓包模块采用独立 `LiveCaptureManager` 管理状态，避免将抓包进程逻辑混入普通预测接口。fallback 路由把输入完整性检查放在预测层，能够向用户解释为什么当前记录使用主模型或兜底模型，这一点提高了系统透明度。

## 4.4 出错原因的分析

项目开发过程中出现的问题主要集中在任务方向变化、数据语义统一、弱类样本不足、模型评价口径和系统集成几个方面。

| 问题 | 主要原因 | 处理措施 |
| --- | --- | --- |
| 前期业务分类结果不能直接用于当前主任务 | 原始目标从业务类型分类调整为加密方法识别，标签语义不同 | 将旧代码归档，重新建立 9 类加密方法标签空间和新脚本目录。 |
| 多源数据合并后部分来源表现偏弱 | 不同数据集原始任务、字段定义和标签纯度不一致 | 保留 `source_name` 供分析，但主模型训练排除该字段，降低来源泄漏。 |
| `TOR`、`FREENET` 等弱类波动较大 | 样本量少、类别分布极不均衡，匿名通信机制之间边界接近 | 使用平滑类别权重、PCAP 子表对比和后续增强建议。 |
| 论文方法和主模型难以直接公平比较 | 论文方法依赖包字节、token 或图结构，全量主表并非都具备这些输入 | 采用全量 9 类主表和 5 类 PCAP 子表两层评价框架。 |
| 实时抓包演示环境不稳定 | Windows 下依赖 Wireshark、Npcap、权限和网卡选择 | 增加 `tshark` 自动发现、管理页状态展示和便携部署说明。 |
| 输入字段缺失导致模型不可用 | 用户提交样本可能缺少 21 个完整数值特征 | 增加 `broad_fallback_xgboost` 和自动路由输出说明。 |

总体看，这些错误和偏差并非单纯编码疏忽，而是由研究任务变化、数据现实约束和系统集成环境共同造成。项目后期通过明确任务边界、分层评价、加强元数据输出和增加 fallback 机制，已经把主要问题转化为可解释、可复查、可继续改进的工程事项。

# 5 经验与教训

本项目最重要的经验是：安全数据分析项目必须先把任务定义和标签语义说清楚，再讨论模型结构。前期业务分类实验虽然取得了一定结果，但当课程目标调整为加密方法识别后，旧标签体系无法继续支撑主结论。及时把旧代码归档、重新定义 9 类标签空间，是项目能够在后期收敛的关键。

第二个经验是：多源数据整合不能只追求“样本都合并进来”，还要持续检查来源差异、标签纯度和数据泄漏风险。项目中保留 `source_name` 作为分析字段，但主模型训练不使用它，这一做法在结果解释和泄漏控制之间取得了较好的平衡。

第三个经验是：课程项目中的软件交付不应停留在单个训练脚本。将模型封装为后端 API、前端页面、CLI 和实时抓包演示后，项目成果更容易被验收人员理解，也更容易复查。尤其是 fallback 路由和管理页状态展示，使系统在输入不完整或环境配置不充分时能够给出可解释反馈。

第四个教训是：弱类样本不足会长期影响安全分类任务的可信度。即使整体 Accuracy 很高，`TOR`、`FREENET` 等小类的召回率和精确率仍然必须单独分析。后续若继续改进，应优先补充弱类数据、增加按抓包文件或采集批次划分的泛化验证，而不是只继续堆叠更复杂模型。

对今后类似项目的建议是：第一，尽早建立统一标签字典和数据清单；第二，每个实验输出都保存 metrics、配置和混淆矩阵；第三，前后端展示应尽早接入最小可用版本，避免最后阶段才发现模型输入输出难以解释；第四，正式报告中的结论必须和数据粒度、输入条件、评价场景一一对应。

# 6 课程评价与建议

通过本项目，项目组对网络流量加密识别任务、公开数据集整合、机器学习建模、论文方法对比和软件系统封装都有了较完整的实践。课程项目的价值不只在于训练一个高分模型，还在于要求学生把需求、数据、模型、系统、测试和报告贯通起来，这对理解信息系统安全中的真实工程问题很有帮助。

对课程的建议主要有三点。第一，建议在项目早期进一步强调“业务分类、协议分类、加密方法识别、密码算法识别”之间的差异，避免学生在选题和标签设计阶段混用概念。第二，建议提供若干可公开使用的小规模 PCAP 样例和验收输入格式，使各组在软件演示时能够更稳定地展示实时或离线预测流程。第三，建议在报告模板之外增加一份优秀项目的指标记录样例，包括数据划分、混淆矩阵、弱类分析和复现命令，帮助学生把实验结果写得更规范。

总体而言，本项目已经完成从研究原型到可演示软件系统的研制过程，形成了较完整的代码、模型、报告和部署说明。后续如继续深化，可围绕弱类数据补强、跨源泛化验证、官方论文方法接入和更稳定的实时抓包部署展开。
